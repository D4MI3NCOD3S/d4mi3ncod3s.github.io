CASE 04

온프레미스 IDC → Azure 전면 이관

기간 2024.03 착수 – 2025.05 안정화 · 컷오버 2025.03.29–30역할 DB 전환 담당 → 선임 퇴사 후 프로젝트 전체 인수 · 완수
Azure SQL MIBlob StorageAzure DNSIISazCopy
ProblemBefore / After위험 분리 · 런북DecisionsContribution · MetricsRelated

Problem

20년 된 서비스 전체가 자체 IDC의 물리 서버 7대(운영 웹 2 · 테스트 · API · 파일 · DB 2)에서 돌고 있었습니다. 2009~2014년 세대 장비에 Windows Server · SQL Server 기술지원 종료로 보안 취약까지 겹쳤습니다. 병의원 · 약국이 매일 쓰는 서비스라 한 번의 심야 컷오버로 끝내야 했고, 코드 곳곳에 파일 경로가 하드코딩되어 있었습니다.

Approach

컷오버 당일에 DB · 파일 · DNS · 애플리케이션을 한꺼번에 바꾸면 문제가 생겨도 원인을 모르고 롤백 지점도 없습니다. 그래서 애플리케이션과 파일 경로 전환을 몇 달 앞당겨 끝내고, 당일에는 DB와 DNS만 넘기도록 위험을 나눴습니다.

BEFORE

  • 자체 IDC 물리 서버 7대 2009–2014년 세대
  • SQL Server 기술지원 종료 · 보안 취약
  • 로컬 파일 서버 코드에 경로 하드코딩
  • 담당자 이탈 선임 퇴사 (2024.11)
→사전 전환당일 최소 변경전수 대조

AFTER

  • Azure 전면 이관 1회차 컷오버 성공
  • Azure SQL MI 호환성 · SQL Agent 유지
  • Blob Storage 설정 스위치로 전환 · 복구 가능
  • 구조적 장애 대책 반복 지연을 해결 방안 보고서로 종결

위험 분리 · 컷오버 당일에 바꾸는 것을 줄인다

컷오버 런북 · 대부분의 구간을 직접 실행

  1. 소스 최신화웹 · API · 배치 · 테스트
  2. 점검 페이지리다이렉트 활성화
  3. DNS 전환기존 → Azure DNS
  4. DB 전환 · 7h백업 → 복사 → 복원 + 파일 azCopy
  5. 이행 테스트자사 + 협력사 공동
  6. 서비스 재개중단 약 12시간 · 재시도 없음

의사결정

모의 실험 먼저

운영 구성을 가상서버로 똑같이 재현해 검증한 뒤 착수. 6단계: 분석 → 모의 실험 → 업체 선정 → 이관 → 오픈 → 최적화

MSP 4사 동일 기준 비교

3년 총비용 · 사후관리 포함 여부 · 방화벽/WAF · 부하 여유 · 라이선스 방식(Windows CSP, SQL Server 2019 vs 2022). 되돌리기 어려운 다년 비용 결정

Azure SQL MI 선택

기존 코드와의 호환성과 SQL Agent 작업을 그대로 유지하기 위해.

"옮겼다"가 아니라 "빠짐없이"

이관 전후 7개 DB의 테이블 · 뷰 · 프로시저 · 함수 · 제약을 객체 단위로 대조. 조용히 빠진 프로시저 하나가 몇 달 뒤에 터지기 때문.

세 번째 장애는 고치지 않고 보고

이관 후 같은 지연이 반복되자 개별 수정 대신 "구조 문제"로 묶은 해결 방안 보고서를 써서 승인받고 종결.
